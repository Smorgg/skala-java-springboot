# 주문 관리 시스템 실습 가이드

기존 User / Product CRUD 코드를 기반으로 **주문(Order) → 결제(Payment) → 배송(Delivery)** 흐름을 직접 설계하고 구현하는 실습입니다.

> **이 가이드를 읽는 방법**
> 이 문서는 정답 명세서가 아닙니다. "무엇을 만들어야 하는지"와 "무엇을 결정해야 하는지"를 알려줄 뿐,  
> 어떻게 만들지는 여러분이 설계합니다. 문서 속 API·속성은 **하나의 예시**이며,  
> 자신의 설계가 이와 달라도 됩니다. 단, 왜 그렇게 설계했는지 설명할 수 있어야 합니다.  

---

## 1. 최종 목표 모습

- 사용자는 상품 목록에서 상품을 선택해 **주문**할 수 있다.
- 주문은 아래 흐름으로 진행되며, 화면에서 상태를 클릭할 때마다 다음 단계로 넘어간다.

```
주문 완료 ──▶ 결제 대기 ──▶ 결제 완료 ──▶ 배송 대기 ──▶ 배송 완료 (끝)
```

- 결제 완료 시점에 결제 정보가, 배송 완료 시점에 배송 정보가 완료 처리된다.
- Thymeleaf 화면 3개(상품 관리, 사용자 관리, 주문 관리)로 전체 흐름을 조작할 수 있다.
- REST API(Swagger UI)로도 동일한 기능을 호출할 수 있다.

## 2. 시작하기 전에 — 기존 코드 이해

새 코드를 짜기 전에 기존 코드가 어떤 패턴으로 작성되어 있는지 10분만 살펴보세요.
Order 쪽을 만들 때 이 패턴을 그대로 따라가면 됩니다.

| 계층 | 기존 코드 | 눈여겨볼 것 |
|---|---|---|
| Entity | `domain/Product.java` | JPA 어노테이션, `@ManyToOne` 연관관계, Enum 상태(`ProductStatus`) |
| Repository | `repository/ProductRepository.java` | 쿼리 메서드 작명 규칙 (`findByStatus`, `findByUserId`) |
| Service | `service/ProductService.java` | `@Transactional(readOnly = true)` + 쓰기 메서드만 `@Transactional`, 연관 엔티티 조회 후 연결하는 방식 |
| Controller | `controller/ProductController.java` | DTO ↔ Entity 변환 헬퍼, `@Valid` 검증 |
| DTO | `dto/ProductRequest/Response.java` | 요청/응답을 Entity와 분리하는 이유 생각해보기 |

**미리 준비할 것**: 화면 작성을 위해 `pom.xml`에 `spring-boot-starter-thymeleaf` 의존성을 추가해야 합니다.
템플릿은 `src/main/resources/templates/` 아래에 두면 됩니다.

## 3. 주요 적용해야 할 기술

| 기술 | 어디에 쓰는가 |
|---|---|
| JPA 연관관계 `@ManyToOne` | 주문 → 사용자, 주문 → 상품 연결 |
| JPA 연관관계 `@OneToOne` (+ cascade 여부는 직접 결정) | 주문 ↔ 결제, 주문 ↔ 배송 |
| `@Enumerated(EnumType.STRING)` | 주문/결제/배송 상태 저장 |
| Enum에 메서드 정의 | 다음 상태 계산, 한글 표시명 등 |
| `@Transactional` + 변경 감지(dirty checking) | 상태 전환 시 save 호출 없이 자동 반영되는지 확인해보기 |
| Spring Data JPA 쿼리 메서드 | 이름 검색, 사용자별 주문 조회 |
| `@Controller` vs `@RestController` | 화면 컨트롤러(뷰 이름 반환)와 API 컨트롤러(JSON 반환) 분리 |

## 4. 스스로 결정해야 할 설계 포인트

코드를 짜기 전에 아래 질문에 대한 자신의 답을 먼저 정하세요. **정답은 없습니다.**  
선택마다 장단점이 있고, 어느 쪽을 골라도 실습 목표는 달성할 수 있습니다.

1. **상태를 어디서 관리할까?**
   - (A) Order에 전체 흐름 상태 하나 (주문완료→결제대기→…→배송완료)
   - (B) Payment / Delivery가 각자 자기 상태만 관리, Order는 이를 조합해서 판단
   - A는 단순하지만 상태가 중복될 수 있고, B는 책임이 분리되지만 "현재 단계" 계산이 복잡해집니다.

2. **결제·배송 정보는 언제 만들까?**
   - 주문 생성 시점에 함께 생성(대기 상태로)? 아니면 결제/배송 단계에 진입할 때 생성?
   - 함께 생성한다면 cascade를 쓸지, Service에서 각각 save할지도 결정하세요.

3. **재고는 언제 차감할까?**
   - 주문 시점? 결제 완료 시점? 재고가 부족하면 어떻게 알려줄까?

4. **연관관계 방향**
   - Order → Payment 단방향이면 충분한가? 양방향이 필요한 조회가 있는가?
   - 양방향으로 간다면 Lombok `@Data`의 `toString()` 무한 순환을 어떻게 피할까?

5. **첫 상태는 무엇으로?**
   - "주문 대기" 상태가 필요할까, 아니면 주문 즉시 "주문 완료"로 시작해도 될까?
   - 화면 흐름(사용자 선택 OK → 주문 완료)과 맞춰서 결정하세요.

## 5. Entity 목록과 역할

속성은 도메인 관점의 필수 항목입니다. 타입·컬럼 설계는 여러분의 몫입니다.

### Order (주문) — 핵심 엔티티
- 역할: 사용자가 상품을 주문한 1건을 표현하고, 진행 상태를 관리한다.
- 속성: 주문한 **사용자**, 주문한 **상품**, **수량**, **진행 상태**, **주문 시각**, 결제·배송과의 연결

### Payment (결제)
- 역할: 주문 1건의 결제 금액과 결제 여부를 관리한다.
- 속성: 결제 **금액**(가격 × 수량), 결제 **상태**, 결제 **완료 시각**

### Delivery (배송)
- 역할: 주문 1건의 배송지와 배송 여부를 관리한다.
- 속성: **배송지 주소**, 배송 **상태**, 배송 **완료 시각**

### 기존 엔티티
- User (사용자): 주문의 주체
- Product (상품): 주문 대상. 주문과 재고의 관계는 설계 포인트 3번 참고

> 참고: `order`는 SQL 예약어입니다. 테이블명을 그대로 `order`로 하면 어떤 일이 생기는지 겪어보고 해결해보세요.

## 6. API 목록과 설명 (예시 설계)

아래는 하나의 예시입니다. 경로·메서드 설계가 달라도 되지만,
**기능(조회/생성/상태전환)이 빠지면 화면을 만들 수 없으니** 기능 목록으로 활용하세요.

### 주문 API (`/api/orders`)
| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/orders` | 전체 주문 조회 |
| GET | `/api/orders/{id}` | 주문 단건 조회 |
| GET | `/api/orders/user/{userId}` | 사용자별 주문 조회 |
| POST | `/api/orders` | 주문 생성 (상품, 사용자, 수량, 배송지) |
| POST | `/api/orders/{id}/next-status` | 상태를 다음 단계로 전환 |
| DELETE | `/api/orders/{id}` | 주문 삭제 |

### 결제 API (`/api/payments`) / 배송 API (`/api/deliveries`)
| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | 목록/단건 조회 | 결제·배송 정보 확인용 |
| POST | `/{id}/complete` | 개별 완료 처리 |

> 생각해볼 것: 결제 API로 직접 완료 처리하면 주문 상태와 어긋날 수 있습니다.
> 상태 변경의 진입점을 하나로 모을지, 어긋남을 허용할지 정하세요.

## 7. 사용자 시나리오 (흐름 ↔ API 연결)

각 화면 동작이 어떤 API(또는 Service 호출)로 이어지는지 점검하는 용도로 쓰세요.

### 시나리오 1: 준비
1. 상품 관리 화면에서 상품 등록
2. 사용자 관리 화면에서 사용자 등록

### 시나리오 2: 주문 생성
1. 주문 관리 화면 진입 → 상품 목록이 보인다
2. 상품의 [주문] 버튼 클릭 → 사용자 선택 화면으로 이동
3. 사용자 선택 + 수량/배송지 입력 후 [OK] → 주문 생성
4. 주문 목록에 "주문 완료" 상태로 나타난다
5. (자신의 설계에 따라) 재고가 줄었는지, 결제·배송 정보가 만들어졌는지 확인

### 시나리오 3: 상태 전환
1. 주문 목록에서 상태 버튼 클릭 → 다음 단계로 전환
2. 결제 완료 단계에서 결제 정보도 완료되는지, 배송 완료 단계에서 배송 정보도 완료되는지 확인
3. 배송 완료 후에는 더 이상 상태가 바뀌지 않아야 한다

## 8. 화면 구성 가이드 (Thymeleaf)

디자인은 자유입니다. 각 화면에 있어야 할 요소만 정리합니다.

| 화면 | 있어야 할 요소 |
|---|---|
| 메인 (`/`) | 3개 관리 화면으로 가는 메뉴 |
| 상품 관리 | 검색 폼, 등록 폼, 상품 목록 테이블(삭제 버튼 포함) |
| 사용자 관리 | 검색 폼, 등록 폼, 사용자 목록 테이블(삭제 버튼 포함) |
| 주문 관리 | ① 상품 목록 + [주문] 버튼, ② 주문 목록 + 현재 상태 버튼(클릭 시 다음 단계) |
| 사용자 선택 | 주문할 상품 정보, 사용자 선택(select), 수량/배송지 입력, [주문 확정] 버튼 |

구현 힌트:
- 화면 컨트롤러는 `@Controller`로 만들고 뷰 이름(문자열)을 반환합니다. `redirect:/view/orders` 패턴도 알아두세요.
- HTML 폼은 GET/POST만 지원합니다. 삭제를 어떻게 처리할지 생각해보세요.
- 여러 화면에 반복되는 상단 메뉴는 Thymeleaf fragment로 묶으면 깔끔합니다. (선택)

## 9. 구현 순서와 단계별 체크포인트

순서는 제안일 뿐이지만, **각 단계의 체크포인트를 통과한 뒤** 다음으로 넘어가는 것을 권합니다.

| 단계 | 작업 | 체크포인트 (여기까지 되면 성공) |
|---|---|---|
| 1 | 상태 Enum 작성 | 상태 전이 로직(다음 상태 계산)을 어디에 둘지 결정했다 |
| 2 | Payment, Delivery 엔티티 | 앱 기동 시 H2 콘솔에 payments, deliveries 테이블이 생긴다 |
| 3 | Order 엔티티 (연관관계) | orders 테이블에 FK 컬럼들이 의도대로 생긴다 |
| 4 | Repository 3개 | 앱이 에러 없이 기동된다 |
| 5 | OrderService (생성 + 상태 전환) | — |
| 6 | REST Controller | Swagger에서 주문 생성 → 관련 테이블 모두에 데이터가 생기고, 상태 전환 API를 5번 호출하면 배송 완료에서 멈춘다 |
| 7 | Payment/Delivery Service·Controller | Swagger에서 결제·배송 조회가 된다 |
| 8 | 화면 (상품 → 사용자 → 주문 순) | 브라우저만으로 시나리오 1~3을 처음부터 끝까지 수행할 수 있다 |

## 11. 심화 과제 (기본 완성 후)

- **주문 취소**: 어느 단계까지 취소를 허용할까? 취소 시 재고는 복원해야 할까?
